# 注入验证记录（含对 Lead 方案的修正）

> 本文记录对 `tools/patch-asar.js` 的独立复验结果，包括 **Lead 最初方案的一个真实缺陷**。

---

## 一、Lead 最初方案的缺陷（已由 patcher 修正）★

### 缺陷

我最初提出的注入方案是「只捕获 webpack require + 文件末尾追加加载器」：

```diff
- n.p="",n(n.s=140)}([
+ n.p="",global.__AURA_REQ__=n,n(n.s=140)}([
```

**问题**：如果官方入口 `n(n.s=140)` **自身抛异常**，整条表达式语句求值失败，
**文件末尾的加载器根本不会执行** —— 注入完全落空，而且悄无声息。

### 实证（我亲自复验，非转述）

| 场景 | 原方案 | patcher 方案 |
|---|---|---|
| 入口抛异常 | LOADER marker = `undefined` ❌ | LOADER marker = `true` ✅ |
| 入口正常 | ✅ | ✅ |

patcher 的修法是把入口调用也包进 try/catch（错误用 `setTimeout` 异步重抛，
**不改变官方「入口异常即终止」语义**）：

```js
n.p="",global.__AURA_REQ__=n,(function(){
  try { return n(n.s=140); }
  catch (__auraEntryErr) {
    try { setTimeout(function(){ throw __auraEntryErr; }, 0); } catch (e) {}
    global.__AURA_ENTRY_ERROR__ = __auraEntryErr;
    return undefined;
  }
})()
```

**结论：这是我方案里的真实缺陷，patcher 的修正是必要且正确的。**

## 二、额外发现：注入后的 bundle 比原版更"抗崩"

在 Linux + 模拟 Electron 环境下对比运行（只桩掉 Linux 加载不了的模块）：

| 测试 | 结果 |
|---|---|
| **A) 未注入的原始 main.js** | ❌ `ERR_INVALID_ARG_TYPE: The "paths[0]" argument must be of type string. Received undefined` |
| **B) 注入后的 main.js** | ✅ **正常运行** |
| **C) 注入状态** | `__AURA_REQ__` = function；`__AURA_SCREENSAVER__` = object；入口错误被记录 |

→ 因为入口异常被 try/catch 接住并异步重抛，**主流程得以继续**，注入也照常安装。
这是该修法带来的额外收益（副作用是"掩盖"了入口错误，但错误仍会异步抛出并记录在
`global.__AURA_ENTRY_ERROR__`，不丢失可观测性）。

## 三、对 patcher 声明的独立核验

| patcher 声明 | 我的核验结果 |
|---|---|
| 注入锚点 `n.p="",n(n.s=(\d+))}([` 全文件唯一 | ✅ 实测 @894，入口 id=140 |
| 末尾以 `]);` 收尾，追加合法 | ✅ 末三字符 `]` `)` `;` |
| 真实 asar 打补丁 + asar 解包回验 | ✅ 注入标记与加载器均存在于产物 |
| `.bak` 保留不覆盖 / `--restore` 可还原 | ✅ |
| 重复打补丁被拒绝且不写文件 | ✅ 靠 injection 标记幂等 |
| loader 单文件自包含 | ✅ 仅 `require('fs')` / `require('path')` |
| **模块 id 硬编码（120/69/40）是遗留风险** | ✅ 属实，且已在 README 与本文记录 |
| **未真机验证** | ✅ 属实（Linux 无法验证原生 FFI） |

### 关于 patcher 对 `src/module/findModule.js` 的批评

patcher 说它的扫描器「在真实 bundle 上会错位（扫出 380 vs 实际 378）」，因此**刻意没有内联**。

我的独立核验：

```
=== findModule 在真实 bundle 上的锚点解析 ===
  taskConstants         expected=38  got=38   verified=true => OK
  windowManager         expected=69  got=69   verified=true => OK
  taskQueue             expected=39  got=39   verified=true => OK
  screenLock            expected=40  got=40   verified=true => OK
  screensaverController expected=120 got=120  verified=true => OK

RESULT: correct=5 mismatch=0
```

**结论**：该扫描器在**锚点定位**这一实际用途上是**正确且经过交叉验证的**
（`verified=true` 表示 moduleId 通过了 `n(<id>)` 引用图交叉校验）。
patcher 关于「内部计数可能偏差」的观察值得记录，但**不影响它能否正确定位目标模块**。

不过 patcher 的选择（不在注入产物里内联扫描器）**仍然合理**：
注入产物越自包含越简单越安全，而模块 id 的重新标定本就该用外部脚本做。

## 四、遗留风险汇总（须在交付时告知用户）

1. **模块 id 硬编码**：`req(120)`/`req(69)`/`req(40)` 已在本版（v1.2.7 / 日志中的 1.2.8.2833）确认。
   换版本后若「注入成功但功能没生效」，需重新 dump 模块 id。
   加载器对每个 `req()` 单独 try/catch，取不到只降级对应能力，不会崩。
2. **未真机验证**：`Verify.json` 实际校验行为、多显示器全屏覆盖、原生 FFI 返回语义
   均无法在 Linux 验证。运行期结论来自「真实 main.js + 模拟 Electron」。
3. 能力 (c) 只切断 `req(69)` 实例上的级联，**不碰 `req(40)`**，
   故云端远程锁屏（messageType 1211）与 `userLock()` 不受影响。
4. 非技术风险：违反 EULA / 官方升级会覆盖 / `BootConfig.needGuard:true` 有守护进程。
